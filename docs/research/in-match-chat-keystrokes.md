# Typing in the match chat with keystrokes

Research note, 2026-10-28. No code was changed. This note answers one question: how can Team Follow type one short line (a map command such as `-ar` or Castle Fight's `!swap 2 5`) into Warcraft III: Reforged's in-match chat by sending keystrokes to the game window, on Windows, macOS and Linux (Proton/Wine)?

Background: the live check for issue 4 (`docs/follow-behaviour.md`, "Live check (issue 4 ...)") showed that `SendGameChatMessage` over the menu websocket does nothing in a match. The menu page is inactive in-game (`IsGameUIActive true`, `DISABLED_SCREEN`). Map commands are read by the map's triggers, which run only in the match. Issues 5 (Same team, `!swap`) and 6 (Game mode, for example `-ar` a few seconds after loading) are blocked on this question. Issues 4 to 6 were read from GitHub web-page summaries because `gh` was blocked in this session. Treat their wording here as paraphrased.

## Summary and recommendation

Keystrokes are feasible on all three systems. Each system needs a different mechanism. Every mechanism shares one limit: Team Follow cannot see whether the chat box is already open or whether the player is typing, unless it reads game memory, which the project forbids for this purpose. The feature therefore stays best-effort, opt-in and visible to the player.

Recommendation:

1. **Windows: `SendInput` from Team Follow itself.** Send the whole line in a single call: open chat (Enter), the text as `KEYEVENTF_UNICODE` characters, then Enter. Before the call, check that the foreground window belongs to the discovered game pid. Never call `SetForegroundWindow`. This is pure Go through `golang.org/x/sys/windows` (`NewLazySystemDLL("user32.dll")`), so it fits the cross-compiled, no-cgo build. No permission prompt is needed.
2. **Linux (Proton/Wine): a Wine-side helper.** Build the same Go `SendInput` code as a tiny Windows `.exe`. Run it with the game's own Proton `wine` and prefix, so it joins the game's wineserver. Wine's `SendInput` goes through wineserver to the Wine foreground thread, not through X11 or Wayland. As a result, it works with Wine's X11 and Wayland drivers on every compositor, needs no prompt, and **cannot reach any non-Wine window**. Inside the helper, check `GetForegroundWindow` → owning process image is `Warcraft III.exe`. One part is unverified and must be tested live before building: how to start the helper so it joins the running wineserver (see Open questions 4 and 5). XTest into XWayland is the fallback if that fails.
3. **macOS: `CGEventPost` guarded by `NSWorkspace.frontmostApplication`.** The game's pid must be the frontmost app. This needs cgo (already used on macOS) and the player's one-time "event synthesizing" grant, which appears in Privacy & Security. Because Team Follow is ad-hoc signed, macOS ties that grant to one exact build ([TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements.md)). Players would have to grant it again after every update. Ship macOS last, or after moving to a stable signing identity.
4. **Reject** `PostMessage(WM_CHAR)`, `/dev/uinput` and the xdg-desktop-portal RemoteDesktop route. The first is unreliable by Microsoft's own account. The other two cannot tell which window receives the keys. The portal route also cannot work on the owner's compositor (niri) today.

Before any of this is built, a new ADR must revise the safety rules (see [What an ADR would have to say](#what-an-adr-would-have-to-say)). The first live test should answer the cheapest decisive question on Windows or under Proton: does the match chat accept `KEYEVENTF_UNICODE` text at all (Open question 1)?

## Observed on the owner's machine (2026-10-28)

The brief assumed KDE. The machine actually runs the following (read from `/proc`, no input sent):

- Compositor **niri 26.04**, `XDG_CURRENT_DESKTOP=niri`. X11 apps run through **xwayland-satellite**, which starts **Xwayland 24.1.14** with `-rootless` and without `-enable-ei-portal`. The Xwayland process has no `LIBEI_SOCKET` in its environment.
- The game runs under **GE-Proton11-7** inside **SteamLinuxRuntime_4** (pressure-vessel). It is launched as a non-Steam shortcut (`SteamAppId=2394312420`, the Battle.net launcher). The Wine processes have `DISPLAY=:1` and `WAYLAND_DISPLAY=wayland-1`, and no `PROTON_ENABLE_WAYLAND`. So Wine uses its X11 driver and the game window is an XWayland window.
- wineserver runs in its own mount namespace (pressure-vessel) but shares the host's pid and network namespaces. `/tmp` is the same tmpfs inside and outside, so the wineserver socket directory `/tmp/.wine-1000/server-*` is visible from the host.
- `/dev/uinput` is `root:root 0660` with an ACL entry `user:mihai:rw-`. That access comes from Steam's `/usr/lib/udev/rules.d/60-steam-input.rules` (`KERNEL=="uinput", ... TAG+="uaccess"`), not from anything Team Follow set up.
- Portal backends installed: `gnome`, `gtk`, `gnome-keyring`. `niri-portals.conf` prefers `gnome;gtk`.

## How the game's chat is opened (what has to be typed)

- Secondary source only: the fan wiki ([warcraft.wiki.gg, Warcraft III: Hotkeys](https://warcraft.wiki.gg/wiki/Warcraft_III:_Hotkeys)) lists Enter "Activate message prompt", Shift+Enter "message prompt to 'All' players" and Ctrl+Enter "message prompt to 'Allies' only", then "Press Enter again to send message". Blizzard's classic hotkey pages on classic.battle.net now return "document not found". **Unverified for Reforged 3.0.1**, including which channel plain Enter uses (Open question 2).
- Whether a map's chat trigger (`TriggerRegisterPlayerChatEvent`) fires for allies-only chat as well as all chat decides which key to use. No primary source was found. **Unverified** (Open question 2).
- The chat box's state (open or closed, half-typed text) lives only in game memory. Reading it to decide what to type would break the rule that discovery reads memory only to find the menu session. So Team Follow has to assume the box is closed. If the player has the box open with half a line, the keystrokes add to that line and send it.
- No command-line option or menu-socket command that posts to the match chat was found. See [Non-keystroke alternatives](#non-keystroke-alternatives).

## Options

### Windows: `SendInput` (recommended)

What the docs say:

- `SendInput` "is subject to UIPI. Applications are permitted to inject input only into applications that are at an equal or lesser integrity level." "This function fails when it is blocked by UIPI. Note that neither GetLastError nor the return value will indicate the failure was caused by UIPI blocking." ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)). If the player runs the game as administrator and Team Follow normally, typing fails with no error. Team Follow cannot detect this, so the window must say "may not have been typed".
- The events of one call "are not interspersed with other keyboard or mouse input events inserted either by the user (with the keyboard or mouse) or by calls to keybd_event, mouse_event, or other calls to SendInput" (same page). Sending Enter + text + Enter in **one** call keeps the player's own key presses from landing in the middle of the line. They can still land just before or just after it. This assumes the game opens the chat box before it handles the next queued character. If the game opens the box on one frame and reads text from the next, the first characters of a burst can be lost. Then the line has to be two calls (Enter, a pause of about 50 ms, then text + Enter), and the player's keys can land in the gap. Open question 1 tests both.
- `KEYEVENTF_UNICODE`: "the system synthesizes a VK_PACKET keystroke", and "Once GetMessage or PeekMessage obtains this message, passing the message to TranslateMessage posts a WM_CHAR message with the Unicode character originally specified by wScan" ([KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput)). This avoids layout lookups for `!`, `-` and digits. It works only if the game's chat reads `WM_CHAR` produced by `TranslateMessage`. **Unverified for Reforged** (Open question 1).
- Fallback if the game ignores `VK_PACKET`: `KEYEVENTF_SCANCODE` "is useful for simulating a physical keystroke regardless of which keyboard is currently being used" (KEYBDINPUT). Map each character with [`VkKeyScanExW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-vkkeyscanexw), which "translates the character using the input language and physical keyboard layout identified by the input locale identifier". Use the game thread's layout (`GetKeyboardLayout(GetWindowThreadProcessId(hwnd))`). Refuse characters that need AltGr or are missing from the layout. Never cut the line short; this matches ADR 0006.
- Focus: Team Follow should not try to bring the game forward. "An application cannot force a window to the foreground while the user is working with another window. Instead, Windows flashes the taskbar button" ([SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)). Stealing focus would also break the "never type into the wrong window" rule from the other side. The guard is: `GetForegroundWindow` → `GetWindowThreadProcessId` → equals the discovered game pid. If not, skip and tell the player. `GetForegroundWindow` "can be NULL in certain circumstances, such as when a window is losing activation" ([GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow)). Treat NULL as "not the game".
- Detection: low-level keyboard hooks see injected keys: "Testing LLKHF_INJECTED (bit 4) will tell you whether the event was injected" ([KBDLLHOOKSTRUCT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-kbdllhookstruct)). The game can tell these keys are synthetic if it wants to. Whether Reforged checks is unknown.

Fullscreen vs windowed: `SendInput` targets the foreground thread whatever the display mode. Minimized or alt-tabbed means not foreground, so the guard skips. Exclusive fullscreen is untested (Open question 7).

Cost: about 100 lines in `infrastructure/` with `platform_windows.go`. The `INPUT` struct is laid out by hand (40 bytes on amd64). No cgo. Tests can cover the event building (characters → `INPUT` array) on every OS if that code sits in an untagged file.

### Windows: `PostMessage(WM_KEYDOWN/WM_CHAR)` (rejected)

Raymond Chen, [You can't simulate keyboard input with PostMessage](https://devblogs.microsoft.com/oldnewthing/20050530-11/?p=35513): posted messages do not update the keyboard shift state, so code that calls `GetKeyState` or `GetAsyncKeyState` "is going to see the 'real' shift state". Dead keys and IMEs make it worse: "The SendInput function was designed for injecting input into Windows." It does not need focus, which sounds attractive, but a game that reads key state directly (Enter to open chat) may ignore it. And typing into a background game the player cannot see is a poor fit for a visible, opt-in feature.

### macOS: `CGEventPost` with a frontmost check (recommended, last)

- Permission: CoreGraphics has a separate "event synthesizing" access, distinct from listening. From `CGEvent.h`: "Checks whether the current process already has event synthesizing access" (`CGPreflightPostEventAccess`) and "Requests event synthesizing access if absent, potentially prompting" (`CGRequestPostEventAccess`), macOS 10.15+ ([header mirror, MacOSX11.3 SDK](https://raw.githubusercontent.com/phracker/MacOSX-SDKs/master/MacOSX11.3.sdk/System/Library/Frameworks/CoreGraphics.framework/Versions/A/Headers/CGEvent.h); Apple's [CGPreflightPostEventAccess](https://developer.apple.com/documentation/coregraphics/cgpreflightposteventaccess()) page has only the declaration). Apple's MDM schema lists `PostEvent` ("use CoreGraphics APIs to send CGEvents to the system event stream") separately from `ListenEvent` and `Accessibility` ([apple/device-management, TCC payload](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.TCC.configuration-profile-policy.yaml)). Input Monitoring is about apps that "monitor your keyboard, mouse, or trackpad" ([Apple Support](https://support.apple.com/guide/mac-help/control-access-to-input-monitoring-on-mac-mchl4cedafb6/mac)), so posting does not need it. Which System Settings list shows the grant (expected: Accessibility) is **unverified**.
- Grants and ad-hoc signing: "Ad hoc signed code ... has a DR but it's tied to that specific version of the code. In both cases macOS can't reliably track the identity of the code" ([TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements.md)). Each Team Follow update would lose the grant. The player would have to remove and re-add it, or the app would prompt again. This is the main cost on macOS. A Developer ID signature removes it.
- Target check: `NSWorkspace.frontmostApplication` "Returns the frontmost app, which is the app that receives key events" ([Apple](https://developer.apple.com/documentation/appkit/nsworkspace/frontmostapplication)). Compare its `processIdentifier` with the discovered game pid.
- Text: build events with `CGEventCreateKeyboardEvent` and set the text with `CGEventKeyboardSetUnicodeString`. Apple warns: "application frameworks may ignore the Unicode string in a keyboard event and do their own translation based on the virtual keycode" ([CGEventKeyboardSetUnicodeString](https://developer.apple.com/documentation/coregraphics/cgevent/keyboardsetunicodestring(stringlength:unicodestring:))). So also set the right virtual keycode for the current layout (via `TISCopyCurrentKeyboardLayoutInputSource` + `UCKeyTranslate`), or limit to characters on the layout. **Unverified** which one the game reads.
- `CGEventPostToPid` (10.11+) is documented only as a declaration ([Apple](https://developer.apple.com/documentation/coregraphics/cgevent/posttopid(_:))). Developer-forum reports say background delivery is unreliable ([thread 724835](https://developer.apple.com/forums/thread/724835); secondary). Not recommended.
- Unlike Windows, events posted at a tap are not batched against user input, so the player's keys can interleave. Keep the line short and post it in one tight loop.

Cost: cgo with CoreGraphics, Carbon (TIS) and AppKit. The macOS build already uses cgo. The window also needs a "Grant permission" step, plus a note after updates.

### Linux A: Wine-side helper (recommended, pending live test)

Idea: ship a tiny Windows program (Go, `GOOS=windows`, no cgo, the same `SendInput` code as the Windows build) inside the Linux binary. Run it with the game's Proton `wine` in the game's prefix. It reads one line, checks that Wine's foreground window belongs to `Warcraft III.exe`, and calls `SendInput`.

What Wine's source shows (gitlab.winehq.org, master):

- `NtUserSendInput` sends each keyboard input with `server_send_hardware_message( 0, SEND_HWMSG_INJECTED, &input, 0 )` ([dlls/win32u/input.c](https://gitlab.winehq.org/wine/wine/-/blob/master/dlls/win32u/input.c)). The wineserver queues it for the desktop's foreground input. With `KEYEVENTF_UNICODE` it sets `vkey = VK_PACKET`, and it marks injected keys `LLKHF_INJECTED` ([server/queue.c](https://gitlab.winehq.org/wine/wine/-/blob/master/server/queue.c), `queue_keyboard_message`). None of this passes through the X11 or Wayland driver. So the helper is independent of the compositor, of XWayland vs Wine's Wayland driver, and of the X keymap. It also cannot reach a non-Wine window.
- The helper must talk to the **same** wineserver: same prefix, same Proton build (client and server protocol versions must match), same user. On this machine the server socket directory is under the shared `/tmp/.wine-1000/`, so a host-side process can in principle reach it. That is an inference from the shared mount, **not tested**.
- Ways to start the helper, in order of preference:
  1. Run Proton's own `files/bin/wine` (the directory of `/proc/<wineserver pid>/exe`) from the host, with `WINEPREFIX` taken from the game's environment. It may fail if the host's libraries do not satisfy Proton 11's binaries, which are built for Steam Linux Runtime 4. Open question 4.
  2. Run it through the runtime: `SteamLinuxRuntime_4/run -- <proton>/files/bin/wine helper.exe`. Heavier (starts a container) but has the right libraries.
  3. Steam's supported "command injection": the player sets `STEAM_COMPAT_LAUNCHER_SERVICE=proton %command%` in the game's launch options. Team Follow then runs `steam-runtime-launch-client --bus-name=com.steampowered.App<id> -- wine helper.exe` ([SLR for game developers, "Inserting debugging commands into the container"](https://gitlab.steamos.cloud/steamrt/steam-runtime-tools/-/blob/main/docs/slr-for-game-developers.md); [steam-runtime-launch-client(1)](https://gitlab.steamos.cloud/steamrt/steam-runtime-tools/-/blob/main/bin/launch-client.md)). This is a documented debugging feature that runs arbitrary commands in the game's container. It is a manual setup step for the player, and broader than this feature needs. Use it only as a last resort.
  Entering the container's namespaces (`nsenter`) needs privileges and is rejected.
- Start the helper once per match (or once per game session) and send it lines on stdin. Do not start a Wine process per line, which takes about a second. It must exit when the game exits. A leftover Wine process keeps wineserver alive, and the game may then look "still running" to Steam (**unverified**).
- Foreground semantics need a live test. Wine's X11 `focus_out` only resets the foreground to the desktop when the window manager does **not** advertise `_NET_ACTIVE_WINDOW` ([dlls/winex11.drv/event.c](https://gitlab.winehq.org/wine/wine/-/blob/master/dlls/winex11.drv/event.c), `focus_out`). xwayland-satellite does advertise it ([src/xstate/mod.rs](https://github.com/Supreeeme/xwayland-satellite/blob/main/src/xstate/mod.rs)). Newer Wine also reacts to `_NET_ACTIVE_WINDOW` changes (`net_active_window_notify` in `window.c`). So after the player alt-tabs to a Wayland window, Wine may still report the game as foreground, and the helper would then type into the game in the background. That is still the game and no other app. But the player would not see it, so the ADR should decide whether that is acceptable. To require visible focus, the host side can also check X focus (Linux B's guard) before handing the line to the helper.

Layout: Unicode via `VK_PACKET` needs no keymap, like on Windows. Wine's `TranslateMessage` turns a `VK_PACKET` `WM_KEYDOWN` into `WM_CHAR` with the character from the high word of `lParam` (`case VK_PACKET: message = ... WM_CHAR ...; NtUserPostMessage( msg->hwnd, message, HIWORD(msg->lParam), ...)` in [dlls/win32u/message.c](https://gitlab.winehq.org/wine/wine/-/blob/master/dlls/win32u/message.c)). As on Windows, this only helps if the game reads `WM_CHAR`.

Timing: the same point as on Windows applies. If the chat box needs a frame to open, the helper must pause after Enter (Open question 1).

Cost: medium. It needs a second `go build` target in the `Makefile` (the helper exe, then `go:embed` into the Linux binary), finding the Proton binaries and prefix from `/proc` (discovery already reads the game's `/proc`), process lifetime, and stdin framing. The `SendInput` code is shared with Windows. No cgo.

### Linux B: XTest into XWayland (fallback)

- XTest events "cause event propagation, passive grab activation, and so on, just as if the corresponding input device action had occurred" ([XTEST extension spec](https://www.x.org/releases/X11R7.7/doc/xextproto/xtest.html)). They go to the X window with input focus, unlike `XSendEvent`, which sets `send_event` and which "many programs observe ... and reject" ([xdotool(1), SENDEVENT NOTES](https://github.com/jordansissel/xdotool/blob/master/xdotool.pod)).
- How rootless Xwayland handles XTest: when built with EI, rootless Xwayland replaces XTest delivery (`xwayland_override_xtest`, [xwayland-input.c](https://gitlab.freedesktop.org/xorg/xserver/-/blob/master/hw/xwayland/xwayland-input.c)). On a client's first fake event it tries the portal, if `-enable-ei-portal` was given, and then `$LIBEI_SOCKET`. If both fail it logs "EI setup failed" and restores normal XTest ([xwayland-xtest.c](https://gitlab.freedesktop.org/xorg/xserver/-/blob/master/hw/xwayland/xwayland-xtest.c)). The man page: `-enable-ei-portal` "has no effect if the compositor doesn't support the relevant XDG portal" ([Xwayland.man](https://gitlab.freedesktop.org/xorg/xserver/-/blob/master/hw/xwayland/man/Xwayland.man)).
  - **niri + xwayland-satellite (this machine)**: neither is set, so XTest is handled inside Xwayland and reaches only X clients. There is no prompt, and keys cannot leak to Wayland-native apps.
  - **KDE Plasma**: KWin runs an EIS socket for Xwayland (`kwin-xwayland-eis-socket.<pid>`). Unless configured otherwise, it starts a prompter asking the player to allow the X client by name ([kwin src/plugins/eis/xwaylandeiscontext.cpp](https://invent.kde.org/plasma/kwin/-/blob/master/src/plugins/eis/xwaylandeiscontext.cpp)). Which Plasma release first shipped this is **unverified**.
  - **GNOME, sway, Hyprland**: not checked. Each starts Xwayland its own way, possibly with `LIBEI_SOCKET` or `-enable-ei-portal`, which would route XTest through the compositor and maybe a prompt.
- Target check: xwayland-satellite sets X input focus to `None` when a Wayland-native window takes focus (`focus_window(x::WINDOW_NONE, ...)` in [src/server/mod.rs](https://github.com/Supreeeme/xwayland-satellite/blob/main/src/server/mod.rs)), and Wine sets `_NET_WM_PID = getpid()` on its windows ([winex11.drv/window.c](https://gitlab.winehq.org/wine/wine/-/blob/master/dlls/winex11.drv/window.c)). The pid namespaces are shared on this machine, so the guard is `GetInputFocus` → walk up to the top-level → `_NET_WM_PID` equals the discovered game pid. Check before every key, because XTest cannot batch like `SendInput`.
- Layout: XTest sends keycodes. Each character must map to a keycode plus Shift (or AltGr) in the **current** keymap (`GetKeyboardMapping`). xdotool remaps a spare keycode for missing characters (`XChangeKeyboardMapping(... scratch_keycode ...)` in [xdo.c](https://github.com/jordansissel/xdotool/blob/master/xdo.c)). Do not copy that. Wine reloads its layouts on every `MappingNotify` and posts `WM_INPUTLANGCHANGEREQUEST` to the focused window ([keyboard.c](https://gitlab.winehq.org/wine/wine/-/blob/master/dlls/winex11.drv/keyboard.c), `X11DRV_KeyboardMappingNotify`), which is a needless disturbance for the game. Refuse characters that are not on the keymap. Players with several layouts (for example us + ru) are a risk: the core keymap does not say which XKB group is active, and `jezek/xgb` has no XKB package. A held Shift on the player's real keyboard also changes the characters.
- Wine's Wayland driver (`PROTON_ENABLE_WAYLAND=1`) makes the game a Wayland-native window, and then XTest does not reach it at all.

Cost: low to medium. Pure Go with `github.com/jezek/xgb` (its `xtest.FakeInput`, `xproto.GetInputFocus` and `xproto.GetKeyboardMapping` exist). No cgo.

### Linux C: xdg-desktop-portal RemoteDesktop + libei (rejected for now)

- "Calling RemoteDesktop.Start presents a dialog to the user". Input then goes through `ConnectToEIS` (recommended) or `NotifyKeyboardKeycode`/`NotifyKeyboardKeysym` over D-Bus. `persist_mode` 2 lets the grant last "until explicitly revoked" with a single-use `restore_token` ([org.freedesktop.portal.RemoteDesktop.xml](https://github.com/flatpak/xdg-desktop-portal/blob/main/data/org.freedesktop.portal.RemoteDesktop.xml)). The D-Bus `Notify*` path would work through `godbus`, which the project already uses, without cgo.
- No method names a target window. Keys go to whatever the compositor has focused, and a Wayland client cannot learn which window that is. The "only the game" rule cannot be met. (A partial guard is possible when the game is on XWayland, using X focus as in Linux B. But then XTest is simpler and needs no dialog.)
- On this machine the portal is served by xdg-desktop-portal-gnome, whose RemoteDesktop backend drives mutter's `org.gnome.Mutter.RemoteDesktop`. niri's D-Bus services (`src/dbus`: `mutter_screen_cast`, `mutter_display_config`, `mutter_service_channel`, `gnome_shell_screenshot`, ...) include ScreenCast but no RemoteDesktop ([niri src/dbus](https://github.com/YaLTeR/niri/tree/main/src/dbus)), so the portal is very likely unusable here. That conclusion comes from the source listing and was not tested live.

### Linux D: `/dev/uinput` (rejected)

uinput "makes it possible to emulate input devices from userspace", and events from the virtual device "will be delivered to userspace and in-kernel consumers" ([kernel docs, uinput](https://docs.kernel.org/input/uinput.html)). It acts like a second physical keyboard. Keys go to whichever window the compositor has focused, nothing can choose or check that window, and the layout is applied after the fact. It needs write access to `/dev/uinput`, which this machine has only because Steam's udev rule grants it. It cannot meet the target rule. Rejected.

### Non-keystroke alternatives

- **Menu websocket**: ruled out by the issue 4 live check.
- **Game command-line options**: none known that post chat. Nothing was found in primary sources.
- **Clipboard paste** (Ctrl+V into the chat box): it still needs Enter keystrokes, it overwrites the player's clipboard, and whether Reforged's in-match chat accepts paste is **unverified**. It only helps with layout issues, which the Unicode routes already solve. Not worth it.
- **Dropping the features**: issue 6's Game mode could become a reminder ("Type -ar now") shown in Team Follow's window or as a desktop notification at the set time. That needs no game access at all. It is a reasonable fallback if the ADR is rejected.

## Typing sequence common to every mechanism

1. Gates from ADR 0006 still apply: Auto-host on, the player hosts this match, the text is fixed by the feature and passes `sendChat`'s limits. Add one more limit for keystrokes: **printable ASCII only** (`0x20`–`0x7E`). That covers every known map command and avoids IME and dead-key problems.
2. Check the target (pid match). If the game is not focused, do not type. Note it once and retry for a short window, for example until 30 s after the scheduled time, then give up with a note. Never steal focus.
3. Send: chat key (Enter, or Shift+Enter if the live test shows maps need all chat), the text, Enter. On Windows and in the Wine helper this is one `SendInput` call, or two with a short pause after the chat key if Open question 1 shows the first characters get lost. With two calls, check the target again before the second. On X11 and macOS, send key by key and check the target before each key. If focus changes mid-line, stop and send nothing more. A half-typed line then sits in the closed or open chat box, so tell the player.
4. Report "Typed -ar in the game chat" only as "sent". The game gives no confirmation that the line was shown.

## Risks

### Terms of use and anti-cheat

- Blizzard's EULA (last revised March 21, 2024) prohibits "bots; i.e. any code and/or software, not expressly authorized by Blizzard, that allows the automated control of a Game, or any other feature of the Platform". It also prohibits "cheats; i.e. methods not expressly authorized by Blizzard ... influencing and/or facilitating gameplay ... and thereby granting you and/or any other user an advantage over other players" ([Blizzard EULA, section 1.C](https://www.blizzard.com/en-us/legal/fba4d00f-c7e4-4883-b8b9-1b4500a402ea/blizzard-end-user-license-agreement)). Typing a chat line on a timer is automated use of a game feature, so it falls within the literal "bots" wording even though it gives no gameplay advantage. The same EULA's "Consent to Monitor" clause says the platform "MAY MONITOR YOUR COMPUTER ... MEMORY FOR UNAUTHORIZED THIRD PARTY PROGRAMS".
- For context, Team Follow already falls under other clauses of the same section: "Data Mining" (discovery reads game memory for the session) and "Unauthorized Connections" (the menu websocket). Keystrokes add exposure under the "bots" wording, but they are not a different category of access from what the app already does.
- No official Blizzard statement about Warden or any other anti-cheat in Reforged was found. Claims that Reforged uses Warden come from fan wikis and player forum posts only, so they are not repeated here as fact.
- Injected input is detectable in principle (`LLKHF_INJECTED` on Windows and in Wine). Whether Reforged looks is unknown.
- Keystrokes write no memory and inject no code, so they keep the project's hard rule. They do drive the game's UI, which is new.
- Mitigation: a separate opt-in per feature with a plain warning; only fixed map commands chosen by the player; at most one line per trigger; never gameplay keys (orders, hotkeys, unit control).

### Typing into the wrong place

- Wrong window: handled by the target check. Mechanisms without a check (uinput, portal) are excluded.
- Chat box already open, or the player typing: undetectable without reading memory. On Windows and in the Wine helper the line cannot be split by the player's keys, but it can merge with text already in the box. Pressing Esc first might close an open box, but Esc may also cancel an order or targeting. **Live test before using it** (Open question 3).
- Wrong channel: Enter vs Shift+Enter (Open question 2). Allies-only output from the map command is fine; a command the map never sees is a silent failure.
- Elevated game on Windows: silent UIPI failure (above).

### What an ADR would have to say

A new ADR ("Typing in the match chat with keystrokes") that amends ADR 0006, and adds to AGENTS.md's safety rules, should state:

- Keystrokes to the game window are a second kind of action that affects the game, next to closing it (ADR 0005). They are allowed only through one contract (for example `contract.GameKeyboard` with `TypeChatLine(ctx, pid, text) error`). Its adapters sit in `infrastructure/` with `platform_<os>.go` files and a mock in `mock/`.
- Only the keys needed to chat: the chat-open key, printable ASCII text, Enter. Never game hotkeys, orders or Esc unless a live test approves Esc.
- ADR 0006's limits and gates stay (host's own Auto-host match, fixed text, 100 characters, no logging of content). Add: printable ASCII only, and off by default with a per-feature opt-in in the window.
- Target rule: before typing (and before each key where sending is not atomic), confirm the keys reach the discovered game process: foreground pid on Windows, Wine foreground image in the helper, X focus `_NET_WM_PID` on XWayland, `frontmostApplication` on macOS. If the check fails, type nothing and tell the player. Never call `SetForegroundWindow` or activate the game. Mechanisms that cannot check the target (uinput, RemoteDesktop portal) are forbidden.
- Nothing reads game memory to learn the chat state.
- The Linux helper runs only in the game's own prefix, only while that game runs, and exits with it. It accepts only lines that pass the same checks again.
- Each OS mechanism is live-tested before it ships, like `verified_builds` gates joining.

## Open questions that need a live test

Run these with a dev-only test command (for example a hidden `wc3-team-follow type-test --after 5s "<text>"`) that is never shipped. Type into a single-player custom game or a private lobby with friends. Never use ladder.

1. **Does the match chat accept `KEYEVENTF_UNICODE` text, and in one burst?** Windows (or the Wine helper): start a custom match, run `type-test --after 5s "-test !-1"`, keep the game focused. Try two variants: (a) Enter, text and Enter in one `SendInput` call; (b) Enter, about 50 ms pause, then text + Enter. Pass: the line appears exactly. Record whether (a) loses the first characters. If text is missing or wrong in both, repeat with the scancode path (`VkKeyScanExW`). Record which path works on 3.0.1.24371.
2. **Which chat key do map commands need, and what does Enter default to?** In Castle Fight with a second human: send `!swap a b` once with Enter and once with Shift+Enter. Note the recipient label the chat box shows for each key and whether the swap happened. Repeat `-ar` (or the map's mode command) in a map that announces modes.
3. **Chat box already open, and Esc.** Open the chat box, type "abc", then run `type-test`. Record the result (expected: "abc-test" is sent). Then test Esc as a first key: with the box open (does it clear and close?), and with a unit selected while in targeting mode (does it cancel the order?). Decide whether Esc is allowed.
4. **Can a host-launched Wine process join the game's wineserver?** No new code is needed for this. Under Proton on this machine, with the game running, note `pgrep -c wineserver` (expect 1). Then run Proton's own Wine with Wine's built-in tools: `WINEPREFIX=<from the game's /proc/<pid>/environ> <proton>/files/bin/wine winedbg --command "info process"`. `<proton>` is the directory of `/proc/<wineserver pid>/exe`, here `~/.local/share/Steam/compatibilitytools.d/GE-Proton11-7-x86_64`. If `winedbg` is missing, use `tasklist.exe` from the same build. Pass: the list includes `Warcraft III.exe`, and `pgrep -c wineserver` is still 1. If it fails with library or protocol errors, try the same command through `SteamLinuxRuntime_4/run -- ...`. Also record whether Steam still shows the game as running if the game exits while a host-launched Wine process is alive.
5. **Wine foreground after alt-tab (niri).** This needs a small probe build of the helper that only prints `GetForegroundWindow`, its pid and image name, and sends no input. Run it with the launch method that passed question 4, and keep `helper --probe --loop` printing once a second. Focus the game, then alt-tab to a Wayland-native window (for example the terminal), then to another XWayland window. Record what `GetForegroundWindow` reports in each case. Decide whether the host-side X focus check is also required.
6. **XTest fallback on niri and KDE.** With `type-test --xtest` and the game focused: pass if the line appears with no prompt on niri. On a Plasma session, record the KWin prompt text and the client name it shows. Also confirm that with focus on a Wayland-native window the guard refuses (X focus is `None`).
7. **Display modes.** Repeat 1 in windowed, borderless (windowed fullscreen) and fullscreen. On Windows, also with the game run as administrator: expect a silent failure, and check that the window's wording ("may not have been typed") is honest.
8. **Layouts.** Repeat 1 (Unicode path) and 6 (XTest) with AZERTY (French), QWERTZ (German) and a two-layout setup (us + ru, switched to ru). Pass: `!`, `-`, digits and spaces come out right, or XTest refuses cleanly.
9. **Timing after load.** For Game mode: type at 0 s, 1 s and 5 s after `IsGameUIActive true`. Record the earliest delay at which the line appears. Also test while the player holds Shift or is mid-word, to see the merge failure.
10. **macOS.** On the native macOS client: the `CGRequestPostEventAccess` prompt and where the grant appears in System Settings; whether the game reads the Unicode string or the keycode; behaviour in fullscreen (separate Space). Then install a rebuilt (re-signed) Team Follow and confirm the grant is lost, as TN3127 predicts.
