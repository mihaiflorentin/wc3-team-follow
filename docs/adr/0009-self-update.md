# 9. Self-update: checking GitHub Releases and asking the player

Status: accepted (2026-10-28). Issues 21 (spec), 22 (the check and the prompt), 23 (download, install and restart) and 24 (What's new).

## Context

New versions come out often, but players only find out by chance, and many run old versions with bugs that are already fixed. Releases are published on GitHub by `.github/workflows/release.yml`: a Release Tag (`X.Y.Z`, optional `v`) makes a stable release with `wc3-team-follow-windows-amd64.zip`, `wc3-team-follow-macos-arm64.zip`, `wc3-team-follow-linux-amd64.tar.gz` and `checksums.txt`; every push to `master` replaces the rolling `edge` pre-release. `CHANGELOG.md` (Keep a Changelog) holds what changed in each version, written for players.

Until now Team Follow talked only to the game, over loopback. Checking for updates is its first request to the internet, so what it sends and where must be narrow.

## Decision

- **Port.** `contract.Updater` has `Latest(ctx)`, which returns the newest stable release (`dto.Release`: tag, notes, the CHANGELOG.md text at that tag, the release page, this system's file and `checksums.txt`). `Download(ctx, release, progress)` returns a verified file, `Install(ctx, path)` replaces the installed app with it, and `Cleanup(ctx)` removes what an earlier update left. The spec's `Restart` is not on the port: the window has to close first, and starting the new version belongs to the composition root and the crash supervisor (below). An error the player can act on implements `contract.UpdateProblem` (`Problem()`, a full sentence). A rate-limit error implements `contract.RetryLater` (`RetryAt`), so the domain waits without parsing messages.
- **Adapter** (`infrastructure/updater`). It reads `GET /repos/{repo}/releases/latest` from `api.github.com`, which skips drafts and pre-releases such as `edge`; it checks `draft` and `prerelease` again. It then reads `CHANGELOG.md` at the release's tag through the contents API (`?ref=<tag>`, `Accept: application/vnd.github.raw+json`); if that fails, the release still counts and its notes stand in. The asset for this system is picked by name (`AssetName`); a release without one, or without `checksums.txt`, leaves those fields empty. Bodies are capped (1 MB release, 512 KB changelog).
- **Network rule.** Only GitHub's own hosts, over HTTPS: the API base must be `https` (the container refuses anything else), the release page and file links must be `https` on `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com` (others are dropped), and the HTTP client follows redirects only to those hosts. Requests carry GitHub's `Accept`, `X-GitHub-Api-Version` and a `wc3-team-follow` User-Agent, and nothing else: no token, cookie, BattleTag, game data or identifier. Each request times out after `[updates] timeout` (20 s).
- **Decisions in the domain** (`domain/update`, pure, driven by the companion with its clock):
  - The running version must be a clean `vX.Y.Z`. A development build (`dev`, a `git describe` version like `v0.7.0-3-gabc1234-dirty`) or an `edge` build (`0.0.0-edge.<sha>`) never checks, and the window says updates are off.
  - A release is offered only when its tag is a clean version newer than the running one (numeric comparison of major, minor, patch) and it has this system's file and `checksums.txt`, which the in-app update needs.
  - Automatic checks run at start-up and every `[updates] check_interval` (6 h) while "Check automatically" is on (the default). A failed check is quiet in the window, is logged, and is retried after `retry_interval` (30 min), or once GitHub's rate limit lifts if that is later. A failure keeps a release already found.
  - "Check for updates" always works on a release build, also with automatic checks off, and answers in the Updates section: up to date, couldn't reach GitHub, rate-limited, or no file for this system. Only one check runs at a time.
  - **Later** hides the banner until a newer release is found or the player checks again; it isn't saved. **Skip this version** saves `skippedVersion`; that version never shows the banner again, a newer one does. The Updates section still shows a skipped or postponed release with an Update button.
  - The banner warns when updating would interrupt play: in a lobby or a match, or with Auto-join or Auto-host on, it says that updating restarts Team Follow and turns Follow off, as every start does.
  - What's new: the changelog sections newer than the running version, up to and including the offered one, newest first (`ChangesBetween`). Without a usable changelog, the release notes are shown instead, as plain text.
- **No Markdown or HTML from the network reaches the page.** `ParseChangelog` turns entries into plain-text spans with only a bold or code flag (link targets dropped, unclosed marks and HTML kept as literal text, sizes capped), and `PlainNotes` flattens the release notes. The page builds nodes with `textContent` only.
- **Saved settings.** `checkUpdates` (stored only when off, so older files load with checks on) and `skippedVersion`, in `friends.json` with the other preferences.
- **Window.** A banner above the status card ("Team Follow X.Y.Z is available", the running version and release date, Update, Later, Skip this version, the warning, and a collapsible What's new with one collapsible section per version) and an Updates section beside Activity (version, status, Check for updates, Check automatically, the releases page). The bridge opens only `https://github.com/` pages taken from the companion's state, never an address from the page.
- **What's new** (issue 24). `CHANGELOG.md` is built into the app: the root package embeds it (`changelog.go`, since `go:embed` can't reach a parent folder) and `main.go` hands it to the companion through `cfg.App.Changelog`, like the build version, so the repository file stays the only copy. `update.WhatsNew` decides on start-up, from the running version, `lastVersion` saved in the preferences and whether settings existed: the first start of a newer version shows "What's new in Team Follow X.Y.Z" with every section after the last version run, up to and including this one, newest first; an install older than this feature (settings, no saved version) shows this version's entries once; a fresh install, a second start and a downgrade show nothing; a development or `edge` build shows nothing and keeps the saved version. The running version is saved at start-up, so it never repeats; settings that couldn't be loaded show nothing and are not overwritten. It works offline. The Updates section reopens it and lists the whole changelog, newest first, with the running version marked. The built-in text goes through the same `ParseChangelog` as the network copy.
- **Release notes.** Each GitHub Release's notes are its tag's `CHANGELOG.md` section and a compare link (`scripts/releasenotes`, docs/ci.md); a tag without a section fails the release workflow, so the before-update prompt and the release page say the same thing.
- **In-app update** (issue 23). Nothing starts without the player's click on **Update**; a development or `edge` build never offers, downloads or installs, and doesn't even run `Cleanup`.
  - **States.** `available` → `downloading` (bytes done and total, Cancel) → `verifying` → `installing` → `restarting`, or `failed`. While an update runs, checks wait and Later and Skip do nothing. Cancel works until the download is verified and goes back to `available`. `failed` keeps the offer and shows the reason (`UpdateProblem`, or one sentence per step that failed), says the running version keeps running, and offers Try again, the releases page and Later.
  - **Download.** Into a temporary folder `.wc3-team-follow-update-*` beside the installed app (the program on Windows and Linux, the `.app` bundle on macOS), so the final rename stays on one volume; creating it also tests that the folder is writable. `checksums.txt` first (capped at 64 KB, sha256sum format), then the release file (capped at 512 MB), hashed while it streams. The URLs must pass the same GitHub-over-HTTPS rule as the check, and so must every redirect. The download has no overall time limit but gives up when nothing arrives for `[updates] timeout`. Progress is reported at most every 100 ms. A file whose SHA-256 differs from `checksums.txt`, or that `checksums.txt` doesn't list, is deleted with its folder: nothing is unpacked or run before the checksum matches.
  - **Unpacking** (`archive.go`) refuses the whole file for an absolute path, a `..` element, a backslash, a write through a link, a link that resolves outside the folder (checked lexically and again with every link resolved), a hard link or a device; `__MACOSX` is skipped, files keep their mode, entries are created with `O_EXCL`, and the total is capped at 1 GB and 10,000 entries. Windows unpacks no links.
  - **Install per system** (`replace.go`, chosen in `platform_<os>.go`; the logic runs in the tests on every system). **Windows:** the running `.exe` is renamed to `<exe>.old` and the new one moved in; if that fails the old one is put back. **macOS:** the whole bundle is swapped with two renames (the old one moves into the temporary folder and is deleted with it), so the icon, `Info.plist` and signature match. A translocated app (`/AppTranslocation/`), a program outside a bundle or a folder Team Follow can't write to is refused before anything is downloaded, with "Move Warcraft Team Follow to the Applications folder". **Linux:** one atomic rename over the old program, with the old one's mode; the file capability from setcap doesn't carry over. Install only takes files from its own temporary folder, and removes it afterwards, also on failure.
  - **Cleanup** at every start of a release build removes `<exe>.old` and leftover temporary folders.
  - **Restart.** On `restarting` the window closes after a moment (`gui.ErrRestart`). On Windows and Linux the window process exits with `crashreport.RestartCode` (75); the supervisor (ADR 0004) treats that as an update, not a crash, starts the program again from the same path as a new, detached instance and exits. On macOS, with no supervisor, the window process does the same through `open -n -a <bundle>`. The new instance gets `WF_RESTART_AFTER=<old pid>` and waits (up to 30 s) for that process to exit before it supervises or opens its window, so it never meets the old single-instance lock; it then marks itself as updated (`WF_UPDATED`). If the new version can't be started, a dialog says so.
  - **WebView2 after the restart (Windows).** WebView2 lets only one browser use a user data folder at a time, and the old window's `msedgewebview2.exe` helpers can outlive the process that exited (WebView2Feedback #2707, #4179: error `0x8007139F`); waiting for the old supervisor alone isn't enough. So the first start after an update waits, before the window starts, until `<data folder>\webview\EBWebView\lockfile` is gone or can be opened without sharing (a running browser keeps it open and deletes it on close), polling every 200 ms for up to 15 s (`crashreport.WaitUntilFree`, `WebviewFree`), and logs `app.webview_wait` with how long it waited and whether the folder got free. As a safety net, the supervisor of that first start retries a window that crashed within its first 10 s once, after the same wait, before showing the crash dialog (`Options.RetryWithin`, `BeforeRetry`). Other systems don't wait.
  - **After the update.** On Linux the window shows the setcap command for the new program with Copy until the player clicks Done; on macOS it says Game mode may need the Accessibility permission again (the ad-hoc signature changes with every build). The banner says the same before updating (`installNote`).
- **Logging.** `update.check` (manual, latest tag, offered version, whether a file and changelog were found), `update.check_failed`, `update.changelog`, `update.later`, `update.skip`, `update.install_start`, `update.downloaded` (bytes), `update.checksum_mismatch`, `update.replaced` (path), `update.installed`, `update.cancelled`, `update.failed` (step, error), `update.cleanup`, `gui.restart`, `app.restart` and `app.webview_wait`. Nothing personal is involved.

## Consequences

- Team Follow now makes outbound HTTPS requests to GitHub, a few per day at most, unless the player turns automatic checks off. Unauthenticated API calls share GitHub's 60-per-hour limit per IP address, which the retry rule respects.
- Nothing is downloaded or changed by the check, only after the player's click on Update.
- `checksums.txt` is the integrity check; the binaries are not code-signed or notarized (a later ADR). A release whose file and `checksums.txt` were both replaced would pass; GitHub's HTTPS and the release's own permissions are what stand behind them.
- Installing needs a folder Team Follow can write to: Program Files on Windows or `/usr/local/bin` on Linux without rights fails with a sentence and the releases page, and leaves the app as it was.
- On Windows `<exe>.old` stays beside the program until the next start. On Linux setcap has to be run again after every update; on macOS the Accessibility permission may have to be granted again.
- During a restart, two instances run for a moment; the new one waits for the old one, so the single-instance lock and the crash supervisor see one window at a time.
- Development and `edge` builds never see an update; testers on `edge` update by hand.
- Releases must keep the asset names and `checksums.txt`, and the release tag's version needs a matching `CHANGELOG.md` section, or the prompt falls back to the release notes.
